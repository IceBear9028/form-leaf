# F01. 에이전트 연결과 문서 접근 허용

상태: 구현 기준안 · 우선순위: P0 · 사용자 여정: UJ-01

[기능 전체](../README.md) · [도구 계약](../tool-contracts.md)

## 1. 문제와 배경

사용자가 에이전트에게 문서 하나의 수정을 맡겼다고 해서 개인 문서 전체의 조회까지 허용했다고 볼 수는 없다. 단순히 로컬 서버 주소만 제공하면 어떤 문서와 동작이 열려 있는지 사용자가 확인하기 어렵다. 반대로 요청할 때마다 같은 허가를 묻는 방식은 반복적인 문서 작업을 방해한다.

사용자는 Formleaf에서 연결별로 문서와 작업 범위를 정하고, 외부 에이전트는 그 범위 안에서 작업한다. 여기서 연결하는 것은 문서 도구이며 모델 계정이 아니다. 사용자의 외부 에이전트는 이미 자신의 방식으로 로그인되어 있다는 전제를 둔다.

## 2. 사용자와 역할

| 행위자 | 책임과 기대 |
|---|---|
| 문서 소유자 | 연결을 만들고 읽기 허용 문서와 쓰기·생성·출력 권한을 정한다 |
| 외부 에이전트 | 발급된 credential로 접속하고 허용한 도구 기능을 사용한다 |
| Formleaf | 모든 요청과 결과 조회에서 최신 권한을 검사하고 폐기를 반영한다 |

첫 대상은 본인 PC의 문서를 관리하고 외부 에이전트 설정을 사용할 수 있는 개인이다. 조직의 사용자 초대·역할 관리와 원격 접속은 비범위다.

## 3. 목표와 성공 기준

- 사용자가 다른 문서를 공개하지 않고 특정 문서의 읽기 또는 수정만 맡길 수 있다.
- 연결 설정에서 현재 권한과 활성 여부를 확인하고, 에이전트에게 요청하지 않고도 폐기할 수 있다.
- 검증 fixture에서 비허용 문서의 본문·이름·목록·오류 상세·출력물이 모두 노출되지 않아야 한다.
- 연결 성공 횟수만 높이기 위해 인증을 생략하거나 전체 문서를 자동 허용하지 않는다.

## 4. 사용 시나리오 — UJ-01

사용자는 이력서 A의 문장 수정을 맡기려고 한다. 같은 workspace의 계약서 B는 공개하고 싶지 않다. Formleaf는 실행 중이며 MCP는 꺼져 있다.

1. 사용자가 MCP 연결 설정을 열어 서버를 켠다. 화면은 실제 endpoint와 시작 성공/실패를 표시한다.
2. '이력서 도우미'라는 연결을 만들고 A만 선택한다. 처음에는 읽기만 허용되어 있다.
3. 사용자가 쓰기와 출력 권한을 켠다. 새 문서 생성과 라이브러리 접근은 별도로 선택한다.
4. 설정 예시와 token을 외부 클라이언트의 개인 설정에 넣는다. Formleaf는 연결 상태를 표시한다.
5. 에이전트가 문맥을 조회하면 A만 사용할 수 있다. B를 열어 둔 경우에는 현재 문서 정보가 비어 있다고 응답한다.
6. 작업이 끝난 뒤 사용자가 연결을 폐기한다. 기존 세션의 다음 요청도 거절된다.

종료 상태: 사용자는 어느 연결에 무엇을 허용했는지 알고 있으며, 요청별 팝업 없이 허용 범위의 작업을 수행했다.

## 5. 상세 요구와 예외

- **F01-R01 — 기본 비공개:** MCP는 기본 비활성이고 새 연결의 문서 집합은 비어 있다. 사용자가 고른 문서와 capability만 저장한다.
- **F01-R02 — 사람이 권한 관리:** token 발급·권한 확대·폐기는 앱 UI에서만 제공한다. 도구 인자로 권한을 덮어쓸 수 없다. create는 write를 함께 요구한다.
- **F01-R03 — 전체 응답 경로 검사:** tools뿐 아니라 초기 문맥, resources, artifact, 작업 조회에도 적용한다. 문서 ID를 추측해 요청해도 존재 여부를 구분해 알려주지 않는다.
- **F01-R04 — 실행 시 재확인:** 접속 때만 검사하지 않는다. 대기 중인 작업은 실행 전에도 현재 grant를 확인한다. 이미 저장된 결과를 권한 폐기로 되돌리지는 않는다. 완료 결과의 재조회는 최신 권한을 따른다.
- **F01-R05 — 복구 가능한 설정 오류:** 포트 충돌은 서버 시작 실패로 표시하고 endpoint가 사용 가능하다고 표시하지 않는다. 앱 종료 시 연결은 종료된다. token 분실 시 기존 것을 폐기하고 새 연결을 설정할 수 있다.

읽기 전용 연결의 수정 요청은 거절한다. 사용자는 앱에서 쓰기를 허용하거나 읽기 작업만 계속할 수 있다. 이 기능은 외부 shell이 가진 OS 권한까지 통제하지 않는다.

## 6. 대안과 트레이드오프

| 대안 | 이점 | 비용·한계 | 판단 |
|---|---|---|---|
| workspace 전체를 하나의 token으로 허용 | 설정이 짧다 | 새 문서까지 의도치 않게 공개될 수 있고 연결별 폐기가 어렵다 | 미선택 |
| 연결별 문서 목록과 capability | 사용자 의도와 허용 범위를 맞추고 독립 폐기 가능 | 문서가 늘면 권한 관리가 필요하다 | 선택, D02 |
| 매 쓰기마다 승인 | 변경 시점에 사람이 검토할 수 있다 | 여러 명령의 반복 승인으로 자동 작업이 끊긴다 | v1 미포함 |

로컬 앱 서버는 설치·문서 상태를 공유하기 쉽지만 Formleaf가 켜져 있어야 한다(D01). 외부 에이전트 자체를 sandbox 안에서 실행하는 기능은 후속 작업이다.

## 7. 범위와 의존성

연결 설정·인증·문서 grant·폐기·상태 표시를 포함한다. AI 로그인·채팅·에이전트 설치는 제외한다. F02–F08의 모든 조회와 변경은 이 권한 경계에 의존한다.

## 8. 인수 조건

| ID | Given — 전제 | When — 행동 | Then — 관찰할 결과 |
|---|---|---|---|
| F01-AC01 | A만 허용, B는 비허용 | B 목록·본문·현재 문맥·resource 요청 | B 이름·내용 없이 null/필터링/동일 접근 오류 |
| F01-AC02 | A 읽기만 허용 | A 수정 요청 | CAPABILITY_DENIED, 저장값 불변 |
| F01-AC03 | 연결된 세션 존재 | 사용자가 token 폐기 후 재요청 | 기존 session ID가 있어도 인증 거절 |
| F01-AC04 | 출력 대기 중 권한이 철회됨 | job 실행 또는 artifact 읽기 | 최신 grant에 따라 거절, 타 문서 정보 노출 없음 |
| F01-AC05 | 포트 사용 중 | MCP 활성화 | 시작 실패와 조치 안내, 성공 표시 없음 |

## 9. 기술 연결과 남은 확인

T01 `get_context` 및 모든 tool/resource의 공통 정책. `accessPolicy`, 서버 lifecycle, 연결 설정 UI로 구현한다. 정확한 grant는 [도구 계약](../tool-contracts.md)의 권한 절을 따른다. 구현 계획 3단계와 연결한다.

설정 화면의 정확한 배치와 token의 로컬 보호 저장 방식은 구현 전 확인할 기술 과제다. 개인 사용자가 문서별 허용 목록을 관리할 수 있다는 가정은 양쪽 클라이언트 연결 시나리오에서 검토한다. 가정이 틀리면 권한 기본값을 넓히기 전에 설정 UX를 개선한다.

기술 실행 흐름: [실행 시퀀스](../runtime-flows.md)의 TB01의 인증·필터링과 TB05의 재조회 권한를 함께 읽는다. 기능 간 의존성은 [설계](../design.md)의 기능 관계 절을 따른다.
