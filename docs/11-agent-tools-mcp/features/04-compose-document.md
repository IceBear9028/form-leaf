# F04. 새 문서를 만들고 섹션 구성하기

상태: 구현 기준안 · 우선순위: P1 · 사용자 여정: UJ-04

[기능 전체](../README.md) · [도구 계약](../tool-contracts.md)

## 1. 문제와 배경

문서 작성에는 문장뿐 아니라 소개·경력·프로젝트 같은 섹션의 순서와 포함 여부를 정하는 일이 있다. 기존 내용 수정 도구만으로는 빈 문서를 만들거나 섹션을 추가할 수 없다. 화면 조작을 흉내 내는 방식은 앱의 현재 화면과 포커스에 의존한다.

에이전트가 문서와 요소를 생성하고 구조를 명시적으로 조정할 수 있게 한다. 모든 순서·부모 관계는 문서 모델 기준으로 처리한다. 새 문서는 목록에 생기지만 사용자가 보던 문서를 자동으로 닫거나 다른 문서를 열지는 않는다.

## 2. 사용자와 역할

문서 작성자는 섹션 구성과 포함할 내용을 요청한다. 에이전트는 container와 콘텐츠 요소로 구조를 만들고 반환된 ID를 다음 요청에 사용한다. Formleaf는 올바른 트리·참조·저장 상태를 검증한다. 문서 이름·초기 내용은 에이전트의 요청 값이고, 내부 ID는 Formleaf가 발급한다.

## 3. 목표와 성공 기준

빈 문서에서 시작해 섹션을 추가·이동·복제하고 필요 없는 섹션을 숨기거나 보관할 수 있어야 한다. 저장 후 재열기에서 구조와 내용이 같아야 한다. root 손상·cycle·잘못된 부모로 인해 읽을 수 없는 문서가 저장되지 않아야 한다. 검증은 임시 workspace의 문서 생성과 트리 변형 시나리오로 수행한다.

## 4. 사용 시나리오 — UJ-04

사용자는 '소개, 경력, 프로젝트 순서의 새 이력서를 만들어줘'라고 요청한다. 연결에는 create/write 권한이 있다.

1. 에이전트가 이름을 정해 빈 문서를 생성한다. Formleaf가 documentId·rootNodeId·revision을 반환하고 연결의 허용 문서에 추가한다.
2. 반환된 root 아래 소개·경력·프로젝트 container를 추가한다. 새 container의 ID를 받는다.
3. 다음 요청에서 각 container에 제목·Markdown 내용을 넣는다. 사용자가 다른 문서를 보고 있어도 진행할 수 있다.
4. '프로젝트를 경력 앞으로 옮겨줘'라는 요청에 현재 구조를 다시 읽고 move_node를 적용한다.
5. '일단 프로젝트는 빼두자'는 요청은 의미에 따라 숨김 또는 보관으로 처리한다. 보관한 요소는 나중에 restore_node로 복원할 수 있다.
6. preview로 순서와 포함 여부를 확인한다. 사용자는 원할 때 문서 목록에서 새 문서를 연다.

전체 대화가 하나의 transaction은 아니다. 각 요청이 저장 단위이므로 중간에 실패하면 이미 완료된 단계는 남는다. 에이전트는 실패 지점부터 현재 구조를 확인해 이어간다.

## 5. 상세 요구와 예외

- **F04-R01 — 빈 문서 생성:** 기존 기본 스타일과 root container로 생성한다. 같은 requestId 재전송은 새 문서를 추가하지 않는다. 생성·index·문서 grant의 장애 복구를 함께 처리한다.
- **F04-R02 — 요소 추가:** container/text/rich-text/markdown/image/repeater를 지원한다. container와 repeater는 비어 있는 상태로 시작한다. 이미지 asset과 repeater 정의는 문서에 이미 존재해야 한다.
- **F04-R03 — 구조 변경:** move/duplicate는 명시한 부모·index에 적용한다. 자기 자손 아래 이동, root 이동·복제·보관, 범위 밖 index는 거절한다.
- **F04-R04 — 숨김·보관 구분:** 숨김은 구조를 유지하며 렌더링에서 제외한다. 보관은 부모와 index를 기록하고 본문 트리에서 분리한다. 보관된 요소의 내용 수정은 복원 뒤 가능하다.
- **F04-R05 — 복원 실패 처리:** 원래 부모가 없어졌거나 보관 상태면 임의 위치로 복원하지 않는다. 해당 오류를 반환하고 사용자가 부모를 먼저 복원하도록 안내할 수 있다.
- **F04-R06 — 생성 결과 확인:** 명령별 새 ID와 영향을 반환한다. 앞 명령이 생성할 ID를 같은 batch의 임시 변수로 참조하는 문법은 제공하지 않는다.

요청 중 실패한 batch는 전부 미반영한다. 사용자가 이미 만들어진 초안을 지우고 싶다면 기존 앱의 문서 관리 기능을 사용한다. 이 MCP 범위에는 문서 삭제 도구가 없다.

## 6. 대안과 트레이드오프

| 대안 | 이점 | 비용·한계 | 판단 |
|---|---|---|---|
| 완성된 임의 문서 JSON 업로드 | 한 요청으로 큰 문서를 만들 수 있다 | 내부 ID·공유 정의·asset 검증 범위가 커진다 | 미선택 |
| 생성 ID를 반환하고 단계별 구성 | 각 단계의 결과와 실패를 설명하기 쉽다 | 부모와 자식을 추가할 때 호출이 늘고 중간 초안이 남는다 | 선택, D04 |
| 모든 제거를 삭제로 통일 | API 종류가 적다 | '잠깐 제외'와 '데이터 제거'의 차이가 사라진다 | node는 숨김·보관·복원 제공 |

요소별 도구를 따로 만드는 대신 apply_operations의 명령으로 묶어 한 문서의 여러 변경을 함께 검증한다. schema는 커지므로 사용 예시와 명령별 설명을 함께 제공해야 한다.

## 7. 범위와 의존성

create/write, F02 구조 조회, F03과 같은 busy/revision 보호에 의존한다. 신규 asset 업로드, 문서 전체 복제·이름 변경·삭제, component 정의 생성은 제외한다. repeater 내용은 F05에서 채운다.

## 8. 인수 조건

| ID | Given | When | Then |
|---|---|---|---|
| F04-AC01 | 빈 workspace와 create/write 연결 | 문서 생성 후 같은 requestId 재전송 | 한 문서·한 root만 생성, 같은 결과 반환 |
| F04-AC02 | 소개·경력·프로젝트가 있는 문서 | 섹션 이동 후 저장·재열기 | 지정한 순서와 콘텐츠 유지 |

| F04-AC05 | 보관 요소의 부모도 보관됨 | 자식 복원 | INVALID_TARGET, 임의 root 삽입 없음 |
| F04-AC06 | 다른 문서를 편집 중 | 새 문서 생성·구성 | 사용자의 열린 문서·선택·포커스 불변 |

## 9. 기술 연결과 남은 확인

T06/T07, add_node/move_node/duplicate_node/set_visibility/archive_node/restore_node. 기존 documentTransactions와 생성 repository 경로를 연결한다. 계획 4-1/4-2에 대응한다.

여러 호출이 필요한 구성 흐름의 실제 호출 수·오류 빈도를 양쪽 외부 에이전트로 확인한다. 복잡한 문서에서 호출 비용이 문제가 되면 batch 내 ID 참조를 별도 설계한다. 이번에 암묵적으로 추가하지 않는다.

기술 실행 흐름: [실행 시퀀스](../runtime-flows.md)의 TB03의 생성 ID·후속 호출과 TB02의 공통 저장를 함께 읽는다. 기능 간 의존성은 [설계](../design.md)의 기능 관계 절을 따른다.
