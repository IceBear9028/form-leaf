# F06. 문서 요소의 스타일 조정하기

상태: 구현됨 · 로컬 검증 근거와 외부 클라이언트 미검증 조건은 [handoff](../handoff.md) 참조 · 우선순위: P1 · 사용자 여정: UJ-06

[기능 전체](../README.md) · [도구 계약](../tool-contracts.md)

## 1. 문제와 배경

문장을 다듬은 뒤에도 글자가 너무 크거나 항목 사이 간격 때문에 페이지가 늘어날 수 있다. 사용자는 '소개 글만 조금 작게'처럼 결과를 요청한다. 에이전트가 CSS나 공유 style을 직접 바꾸면 문서의 다른 부분도 바뀌거나 출력에서만 깨질 수 있다.

이 기능은 현재 모델이 표현할 수 있는 스타일 속성을 지정한 문서 node에만 적용한다. 공유 style을 쓰고 있으면 복사해 분리한 뒤 변경한다. 스타일 변경이 실제 페이지에 미치는 영향은 F07에서 확인한다.

## 2. 사용자와 역할

작성자는 시각적 의도와 대상 범위를 지정한다. 에이전트는 현재 style과 문서 구조를 읽고 허용된 속성으로 변경안을 만든다. Formleaf는 단위·enum·값 범위·font·색 참조를 검사한다. 자연어의 '조금'을 몇 pt로 바꿀지는 외부 에이전트가 판단하고 사용자에게 설명할 영역이다.

## 3. 목표와 성공 기준

한 node의 스타일 변경이 공유 style을 쓰는 다른 node를 변경하지 않아야 한다. 문서 내용은 유지되고 유효한 모델만 저장되어야 한다. 글자 크기·간격·페이지 나눔 등의 변경은 snapshot preview와 PDF에 동일하게 반영되어야 한다. 무조건 페이지 수를 줄이는 것을 성공으로 삼지 않으며 가독성·내용 잘림을 함께 확인한다.

## 4. 사용 시나리오 — UJ-06

사용자는 '소개 문단 글자를 작게 하고 경력 항목 사이 간격을 줄여줘'라고 요청한다. 문서는 idle이며 write/render가 허용되어 있다.

1. 에이전트가 대상 node와 연결된 현재 style을 읽는다. 단일 요소인지 component 내부 공통 서식인지 구분한다.
2. 소개 node의 typography와 경력 repeater/container의 gap 등 모델이 지원하는 속성으로 변경안을 만든다.
3. 필요한 경우 dryRun으로 속성과 영향받는 node를 확인한다.
4. Formleaf가 공유 style을 분리하고 patch를 적용해 저장 revision을 반환한다.
5. 에이전트가 새 revision의 preview를 확인한다. 줄바꿈·페이지 수가 의도와 맞지 않으면 현재 값을 다시 읽고 별도 수정한다.

종료 상태: 선택한 범위의 서식과 그 결과를 확인할 수 있다. '이 문서를 반드시 한 페이지로' 같은 최적화 결과는 보장하지 않는다.

## 5. 상세 요구와 예외

- **F06-R01 — 지정 범위 적용:** 문서 트리의 node만 직접 style 수정 대상이다. component 정의 내부 node는 제외한다. instance/container 외곽 스타일과 내부 정의 스타일을 혼동하지 않는다.
- **F06-R02 — 공유 style 분리:** 다른 node가 같은 styleId를 참조하면 새 style을 복사해 대상에 연결한 뒤 patch한다. 대상 자식은 부모 레이아웃·상속의 영향을 받을 수 있으므로 preview로 확인한다.
- **F06-R03 — 닫힌 속성:** layout/typography/markdown/decoration/pagination의 기존 속성만 허용한다. raw CSS·HTML·외부 font 설치는 받지 않는다.
- **F06-R04 — patch 의미:** 객체는 깊이 병합, 배열은 교체, leaf null은 제거다. 삭제한 속성은 기존 렌더러의 기본값·상속 규칙을 따른다. id/name은 수정하지 않는다.
- **F06-R05 — 저장 보호:** 범위 밖 숫자·알 수 없는 token/font는 거절한다. busy/revision/batch 규칙은 다른 수정과 동일하다.

원하는 서식이 현재 모델의 Markdown theme 속성에 없다면 지원하지 않는다고 설명한다. CSS 문자열로 우회하거나 component 정의를 묵시적으로 수정하지 않는다.

## 6. 대안과 트레이드오프

| 대안 | 이점 | 비용·한계 | 판단 |
|---|---|---|---|
| raw CSS 패치 | 표현 범위가 넓다 | 앱 모델 밖 상태와 화면/PDF 불일치를 관리해야 한다 | 미선택 |
| 공유 style 직접 변경 | 여러 요소를 한 번에 통일할 수 있다 | 특정 요소만 바꾸려는 요청의 범위를 넘기 쉽다 | v1 미포함 |
| typed patch + 사본 분리 | 대상 범위를 예측하고 기존 렌더러 재사용 가능 | style 수가 늘며 모델 밖 표현은 불가 | 선택 |

자동 레이아웃 최적화 대신 에이전트의 수정→preview 반복을 허용한다. 호출 횟수가 늘지만 사용자가 원하는 결과와 단계별 변경을 연결할 수 있다.

## 7. 범위와 의존성

F02의 구조·style 조회, F03의 저장 보호, F07의 결과 확인을 사용한다. 공유 스타일 일괄 수정, component 내부 theme 전체 변경, 신규 font 설치는 제외한다.

## 8. 인수 조건

| ID | Given | When | Then |
|---|---|---|---|
| F06-AC01 | A/B가 같은 style 참조 | A의 fontSizePt 변경 | A에 사본 연결, B의 style 값과 참조 유지 |
| F06-AC02 | 기존 style의 여러 속성 존재 | 일부 patch 적용 | 지정 속성만 변경, 미지정 속성 유지 |
| F06-AC03 | 허용되지 않는 값·CSS 키 | patch 요청 | validation 오류, 저장값 불변 |
| F06-AC04 | component 정의 내부 node | style 변경 요청 | INVALID_TARGET, 공유 정의 불변 |
| F06-AC05 | 유효한 스타일 변경 저장 | 같은 revision preview/PDF | 변경된 스타일 반영, 기존 본문 내용 보존 |

## 9. 기술 연결과 남은 확인

T03/T07/T10, update_node_style 및 StylePatch. 기존 updateNodeStyle 앞에 사본 분리 로직이 필요하다. 계획 4-3과 연결한다.

일부 글꼴의 실제 출력 품질과 플랫폼별 설치 font 차이는 hidden renderer 시험으로 확인한다. 지원 font 목록의 결정은 구현 과제이며 확인하지 않은 글꼴을 지원한다고 문서에 추가하지 않는다.

기술 실행 흐름: [실행 시퀀스](../runtime-flows.md)의 TB02의 사본 변경·저장과 TB04의 결과 출력를 함께 읽는다. 기능 간 의존성은 [설계](../design.md)의 기능 관계 절을 따른다.
