# F08. 연결 중단 후 작업 결과 확인하기

상태: 구현됨 · 로컬 검증 근거와 외부 클라이언트 미검증 조건은 [handoff](../handoff.md) 참조 · 우선순위: P0 · 사용자 여정: UJ-08

[기능 전체](../README.md) · [도구 계약](../tool-contracts.md)

## 1. 문제와 배경

새 항목을 추가한 직후 연결이 끊기면 에이전트는 저장 여부를 모른다. 오류처럼 보인다는 이유로 같은 의도의 요청을 새 ID로 다시 보내면 문서·항목·출력물이 중복될 수 있다. 반대로 응답이 없었다고 '변경되지 않았다'고 말하는 것도 사실과 다를 수 있다.

이 기능은 작업 의도를 식별하는 requestId와 영속 journal을 이용해 이미 한 작업의 결과를 확인하게 한다. 대화 기록 재개나 편집기의 undo를 제공하는 기능과는 별개다.

## 2. 사용자와 역할

작성자는 변경 여부와 다음에 할 일을 알아야 한다. 에이전트는 쓰기·출력 전에 requestId를 만들고 재접속 뒤 같은 ID를 유지한다. Formleaf는 저장 여부를 근거로 상태를 반환하고 불확실한 작업을 자동 중복 실행하지 않는다.

에이전트가 requestId를 잃어버린 경우의 자동 추정은 제공하지 않는다. 사용자는 앱의 최근 작업 요약과 문서 상태를 확인할 수 있으나 이를 과거 대화 전체의 복원으로 표현하지 않는다.

## 3. 목표와 성공 기준

- 같은 연결 credential과 requestId·입력으로 재요청해도 부작용을 반복하지 않는다.
- 저장 완료와 화면 반영 완료를 구분하고, 저장 여부를 모르면 불확실성을 표시한다.
- 실패 주입 시험에서 새 문서 생성·항목 추가·PDF 출력의 중복을 방지한다.
- 인증값·본문을 기록하지 않고도 사용자가 작업 이름·대상·진행 상태를 확인할 수 있다.

## 4. 사용 시나리오 — UJ-08

에이전트가 경력 항목 추가를 요청했지만 결과를 받기 전에 연결이 끊긴다.

1. 에이전트는 호출 전에 만든 requestId를 보관한다. 연결 중단을 취소나 저장 실패로 단정하지 않는다.
2. 같은 credential로 다시 연결하고 get_operation에 원래 requestId를 보낸다.
3. completed이면 저장 revision과 생성된 itemId를 받아 이후 작업을 계속한다. pending이면 새 항목을 또 만들지 않고 결과를 다시 확인한다.
4. failed이고 outcome이 not_committed이면 실패 원인을 해결하고 수정한 요청을 새 ID로 보낼 수 있다.
5. recovery_required 또는 outcome unknown이면 자동 재실행을 멈추고 앱의 복구 상태와 문서를 확인한다. 새 ID로 우회하지 않는다.
6. 저장됐지만 UI 반영이 확인되지 않은 경우 사용자는 저장 성공과 화면 갱신 상태를 각각 확인한다.

종료 상태: 성공·미저장 실패·복구 필요 중 실제 근거에 맞는 상태가 전달된다. 복구 불명 상태를 성공처럼 숨기는 것은 완료가 아니다.

## 5. 상세 요구와 예외

- **F08-R01 — 영속 요청 identity:** MCP session ID가 아닌 credential의 영속 ID + requestId로 구분한다. 같은 정규화 입력은 기존 결과 또는 pending을 반환하고, 다른 입력은 REQUEST_ID_REUSED로 거절한다.
- **F08-R02 — 저장 경계 기록:** create_document, 실제 apply_operations, export_pdf를 journal에 기록한다. dryRun은 저장·journal·artifact를 만들지 않는다. 앱 재시작 후 저장 snapshot과 기록을 재조정한다.
- **F08-R03 — 상태의 의미:** pending/completed/failed/recovery_required와 outcome을 구분한다. failed는 미반영이 확인된 경우만 사용한다. 불명 상태에서 자동으로 명령을 재실행하지 않는다.
- **F08-R04 — UI 확인 분리:** persisted=true, uiSynced=false는 저장 실패가 아니다. 사용자와 에이전트는 재저장으로 해결하려 하지 않고 현재 저장본과 화면 상태를 확인한다.
- **F08-R05 — 조회 권한 유지:** 같은 credential과 현재 문서 권한이 필요하다. token 폐기나 문서 권한 철회 이후 과거 결과 조회로 문서를 다시 읽을 수 없다.
- **F08-R06 — 결과 화면:** 최근 작업의 이름·상태·허용 문서·revision과 출력 결과를 표시한다. 본문·token을 운영 로그에 넣지 않는다. 작업 기록은 사용자용 문서 history나 undo stack이 아니다.

연결 중단과 클라이언트 취소 신호는 이미 저장된 변경을 되돌리지 않는다. 이번에는 별도 취소 도구를 제공하지 않는다. PDF artifact가 만료되어도 작업 완료 기록은 유지하며, 장기 보관이 필요하면 F07의 앱 저장 기능을 사용한다.

## 6. 대안과 트레이드오프

| 대안 | 이점 | 비용·한계 | 판단 |
|---|---|---|---|
| 실패처럼 보이면 새 요청 재실행 | 구현이 간단하다 | 응답 유실과 미저장을 구분하지 못해 중복 생성 | 미선택 |
| MCP session 메모리에 결과 보관 | 연결 내 재전송 처리 용이 | 앱·세션 재시작 때 결과 소실 | 미선택 |
| 영속 journal과 같은 ID 재조회 | 재접속·재시작을 넘는 결과 확인 | 저장 순서·복구 코드와 디스크 관리 필요 | 선택, D07 |

첫 버전은 journal을 자동 삭제하지 않는다. 오래된 requestId 재전송의 의미를 보존하는 대신 기록이 늘어난다. 보관 기간을 제한하려면 만료된 요청 ID를 어떻게 거절할지도 함께 설계해야 한다.

## 7. 범위와 의존성

F01의 credential·grant와 공통 저장 service가 기반이다. F03–F07의 부작용 있는 요청에서 사용한다. 제공사 대화 복원·작업 자동 취소·AI 변경 되돌리기·장기 이력 탐색 UI는 후속이다.

## 8. 인수 조건

| ID | Given | When | Then |
|---|---|---|---|
| F08-AC01 | 항목 추가 저장 후 응답 유실 | 같은 ID·입력 재전송/결과 조회 | 항목 하나, 같은 생성 ID와 revision |
| F08-AC02 | 이미 사용한 requestId | 다른 입력 전송 | REQUEST_ID_REUSED, 추가 변경 없음 |
| F08-AC03 | 저장 경계에서 앱 중단 | 재시작 후 조회 | 증거에 맞는 복구 결과, 확인 불가 시 recovery_required, 자동 중복 실행 없음 |
| F08-AC04 | 저장 완료·UI acknowledgement 유실 | 결과 조회 | persisted=true/uiSynced=false를 구분하여 반환 |
| F08-AC05 | 완료된 작업과 새 MCP session | 같은 credential 또는 다른 credential로 조회 | 같은 credential은 현재 권한 범위에서 조회, 다른 credential은 거절 |
| F08-AC06 | 입력 검증 실패 또는 저장 여부 불명 | 사용자에게 결과 표시 | 미저장 실패와 복구 필요를 구분, 본문·token 로그 없음 |

## 9. 기술 연결과 남은 확인

T06/T07/T11의 requestId와 T12 get_operation. 계획 2단계에서 journal·복구, 3단계에서 조회, 5단계에서 결과 UI, 6단계에서 재연결을 검증한다.

원자적 파일 교체·문서 index·새 문서 grant·journal의 실패 순서는 실제 repository 경로를 기준으로 fault injection으로 확인해야 한다. 준비·canonical/index·grant·journal 완료 경계의 실패를 테스트했고 손상된 staged snapshot은 recovery_required로 유지한다. 모든 OS/파일시스템 장애를 복구한다고 보장하지 않는다.

기술 실행 흐름: [실행 시퀀스](../runtime-flows.md)의 TB05의 journal 재조정과 도구 계약의 상태도를 함께 읽는다. 기능 간 의존성은 [설계](../design.md)의 기능 관계 절을 따른다.
