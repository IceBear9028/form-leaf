# F03. Promise 완료와 실패 책임

## 1. 문제와 사용자

**void만 붙인 호출은 실패 처리나 후속 동작의 순서를 보장하지 않는다.**

- 목표: 개발자가 호출 문맥별 완료·결과·실패 소유자를 명확히 한다.
- 사용자: 제품·테스트를 수정하는 개발자와 리뷰어, 해당 동작을 사용하는 문서 편집 사용자.

## 2. 사용 흐름과 요구

**수정 후 검사를 실행하고 동작 계약까지 확인한다.**

1. 사용자가 저장 후 화면 닫기처럼 비동기 작업에 이어지는 동작을 요청한다.
2. 호출자는 완료와 성공 결과를 확인한 뒤 후속 동작을 수행한다.
3. 실패하면 기존 오류 표시와 초안을 유지하고 재시도할 수 있게 한다.

- 함수 계약과 호출 문맥을 함께 판단한다.
- no-floating-promises는 ignoreVoid=false로 적용한다.
- 빈 catch나 기계적인 await 추가를 해결로 삼지 않는다.

## 3. 범위·대안·의존성

- 정책 추적: D01, AC02·AC03; 정확한 설정값은 [공통 정책](../implementation/policy.md)이 소유한다.
- 선행 기능: F02.
- 제외: 다른 기능의 규칙 수정과 사용자 데이터·schema migration.
- 선택 이유: 모든 void 허용은 실패를 숨기고 모든 await 강제는 실행 의미를 바꾼다. 호출 책임별 수정과 좁은 예외를 선택한다.
- 실패 시: 기존 저장·편집 계약을 유지하고 이 기능의 수정 범위에서 재검토한다.

## 적용 결과

두 Promise 규칙을 error로 활성화했다. UI 분리 실행은 runAction에서 rejection을 받아 오류 toast·진단을 남기며, 저장 timer/단축키는 기존 save-state store에서 dirty·error 상태를 보존한다. 저장 후 닫기·내보내기·화면 복귀의 완료 대기와 boolean 검사는 유지했다. main의 외부 URL·창 로딩·초기화·background output·HTTP 정리에는 작업별 실패 경계를 추가했다.
