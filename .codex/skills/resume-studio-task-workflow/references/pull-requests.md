# PR 작성 규칙

PR은 해당 변경을 리뷰하기 위한 요약이다. 현재 최종 diff를 기준으로 문제·사용자 결과·기능별 전후 차이를 먼저 설명하고, 세부 기획과 구현 설계는 링크한다. 대화 기록이나 커밋을 전부 읽어야 이해되는 본문을 만들지 않는다.

## 원본과 정보의 기준 위치

- GitHub 본문 양식의 단일 원본은 [PULL_REQUEST_TEMPLATE.md](../../../../.github/PULL_REQUEST_TEMPLATE.md)다. assets에 별도 PR 사본을 만들지 않는다.
- 기획은 features/, 기술 구조와 코드 변경 의도·구현 방식은 implementation/, 진행·기능별 커밋은 plan, 실제 검증 근거와 재개 지점은 handoff가 소유한다. PR에는 리뷰에 필요한 요약만 둔다.
- 제목은 최종 변경을 한 문장으로 표현한다. 범위가 달라졌다면 제목과 본문을 함께 고친다. 임시 우회나 폐기한 접근의 작업 일지를 나열하지 않는다.
- PR 본문에서는 파일 경로만 적은 상대 링크 대신 `https://github.com/<owner>/<repo>/blob/<commit-or-branch>/docs/...` 링크를 사용한다. 과거 검증 근거는 해당 커밋으로 고정한다. 저장소 안 문서는 상대 링크를 유지한다.

## 규모에 따른 작성

| 작업 | 남길 내용 | 생략 가능한 내용 |
|---|---|---|
| 오타·링크·단일 조건 수정 | 문제와 전후 차이를 담은 짧은 요약, 실제 검증과 미실행 이유 | 별도 비교표·설계 결정·전환 절·새 docs 세트 |
| 여러 코드 경계나 기능을 변경 | 작업 요약, 기능별 As-Is/To-Be, 핵심 코드와 리뷰 순서, 검증·한계, 관련 docs | 영향이 없는 migration/rollback 절 |

As-Is/To-Be는 같은 사용자 행동이나 실패 상황을 비교한다. '파일 추가 → 구현 완료' 같은 진행 상태 비교를 쓰지 않는다. 기능 ID는 관련 기획과 설계에 대응시키되 11번의 기능 수·도구 수를 다른 작업에 강제하지 않는다. 표의 To-Be에는 실제 PR에서 구현한 결과만 적고 예정된 기능은 분리한다.

핵심 코드 설명에는 리뷰어가 먼저 볼 파일·symbol, 변경 목적, 선택 이유와 비용을 포함한다. 전체 파일 목록과 함수별 상세를 복제하지 않는다. 중요한 실패·저장·호환성 경계는 짧게 드러내고 구현 설계로 연결한다.

## 검증 근거 작성

각 결과에 실행일, 대상 커밋(미커밋이면 기준 HEAD와 작업 트리 변경), 명령·실행 위치, 환경, 관찰 결과를 기록한다. 실패 후 재실행했다면 최종 결과와 남은 한계를 구별한다. 문서 검사 통과를 제품 동작 통과로 확대하지 않는다.

기존 결과를 인용하면 당시 날짜·커밋·근거 링크와 인용 이유를 적는다. 다른 커밋에서 실행한 여러 검사를 최신 HEAD에서 모두 실행한 것처럼 합치지 않는다. 건너뛴/미실행 검증과 이유는 명시한다. 문서만 바뀌면 제품 시험을 관성적으로 재실행하지 않는다.

## 적용 예시 — 작성 방법 설명용

아래는 형식 예시이며 실제 수행 결과가 아니다. 실제 PR에서는 관련 diff·커밋·명령·결과와 유효한 문서 링크로 작성한다.

### 작은 문서 수정

> 문서 이동 후 템플릿 안내 링크가 예전 경로를 가리켜 열리지 않았습니다. 링크를 현재 경로로 바꿔 작업 문서에서 템플릿을 바로 찾을 수 있게 했습니다.
>
> 검증에는 실제 실행일·기준 HEAD와 수정 작업 트리, 상대 링크 검사 명령과 결과를 기록합니다. 제품 코드를 바꾸지 않아 제품 시험은 실행하지 않았다고 명시합니다.

전후 차이가 요약에 있으므로 비교표와 새 설계 파일은 필요 없다.

### 여러 기능의 변경

기획·구현 설계가 분리된 작업이라면 다음처럼 기능별로 읽게 한다. 아래 동작은 가상의 예시다.

| 기능·상황 | As-Is | To-Be | 리뷰 연결 |
|---|---|---|---|
| F01 저장 충돌 | 오래된 화면의 저장이 최신 내용을 덮어씀 | revision 불일치를 거절하고 입력 초안 유지 | F01 기획과 구현 설계, 저장 service |
| F02 결과 확인 | 응답 유실 시 저장 여부를 알 수 없음 | 요청 ID로 기존 결과를 조회 | F02 기획과 구현 설계, 결과 조회 경로 |

이후 공통 저장 경로→각 기능 호출부→충돌/재시도 검증 순서로 핵심 파일과 목적을 요약한다. CAS를 선택한 이유와 자동 병합을 제공하지 않는 비용은 구현 설계로 연결한다. 실제 검증 표와 미실행 환경을 적고, 저장 형식 변경이 있을 때만 전환·복구 절을 남긴다.

## 제출 전 확인

최종 diff와 요약의 범위가 같은지, As-Is/To-Be가 관찰 가능한 행동인지, 링크가 리뷰할 코드를 가리키는지 확인한다. 빈 표·주석·placeholder와 해당 없는 절을 제거한다. PR 작성 요청과 커밋·push·PR 생성·병합 권한은 현재 사용자 지시에서 각각 판단한다. 템플릿 자체가 외부 작업 권한을 부여하지 않는다.
